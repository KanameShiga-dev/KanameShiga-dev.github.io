AI 開発の実践

AI に「作らせる」段階から、AI が仕事をできる環境と、それを管理する仕組みを作る段階へ進んできました。

実装例 ／ ローカル開発運用基盤

采来 — サイクル —

Codex や Claude Code などの AI 開発ツールを統括し、作業の状態・引き継ぎ・検証結果・判断をブラウザで管理する仕組みです。AI やモデルが変わっても、作業を続けられる状態を残すことを目的にしています。

  • 開発の依頼を工程と担当に分け、作業ボードで停止理由や承認待ちを確認する
  • モデルの切り替えやセッションの交代を、引き継ぎの記録（Handoff）でつなぐ
  • プロジェクト台帳から Harness（作業範囲・制約・完了条件）を生成・補完する
  • Git の差分を使い、AI に渡すコンテキストを減らす運用
  • Ollama による判断の候補を、採用せずに記録して比べる（シャドー評価）
  • 削除・公開・外部送信・権限変更は、人が確認してから行う

Harness：AI に働く環境を与える

AI の性能に頼るのではなく、AI が行動できる範囲を設計します。

Harness = Goal + Context + Rules + Tools
  + Permissions + Workflow + Feedback + Verification

AI が「終わったと思ったら終わり」ではなく、完了の条件（Definition of Done）を満たしたら終わる形にしています。

観察→実装→検証→修正↺

Decision Layer：すべてを LLM に考えさせない

ルールや小さな判断モデルで済む処理は軽く扱い、必要なときだけ LLM を使います。応答の遅さ、トークン、コストを減らすための設計です。

Policy→Risk Gate→Decision→Router→Worker→Test→Eval

RPA では、画面の状態の判断を AI に任せ、定型の操作は RPA に任せる形に分けて、画面の変更に強くしています。

Claude Code と Codex の併用

2 つのエージェントが同じ方針ファイル（AGENTS.md）を読み、引き継ぎは HANDOFF.md 1 本で行う運用を作りました。

個人設定は GitHub の private リポジトリで同期し、PC を移るときは再生成できないものだけを約 1MB にまとめて運びます。

既存プロジェクトの Harness 化

増えたプロジェクトを、読み取り専用の調査 → 分類 → 変換の順で管理下に入れます。

読み取り調査→分類→AGENTS / GOAL / SCOPE / DoD / Tests

セキュリティ監査を AI に任せるときも、最初は変更権限を渡さず、読み取りだけで調べさせます。

大切にしていること

どのプロジェクトでも、繰り返し使ってきた進め方です。

確かめられる仮説は、実装より先に確かめる実機での動きはメモリやログの実測で、データの版は稼働中のサーバーから読み取って確かめます。
配っているものと直したものが同じかを確かめる設置や更新のあとに、配られているファイルが修正後のものかをハッシュで照合します。確認していないことは「未確認」と書き分けます。
戻し方を先に用意する公開や設置の前に、影響と元に戻す手順を書き、承認を得てから実行します。
処理の性質に合わせて役割を分けるすべてを LLM に任せず、ルール、小さなモデル、RPA、人の確認を組み合わせます。
